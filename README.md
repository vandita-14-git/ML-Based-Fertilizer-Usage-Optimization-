# Where does more fertilizer stop paying off?

**A machine-learning method demonstration on a synthetic crop-yield dataset**

![Project pipeline](images/flow_01_pipeline.png)

This project teaches a computer to predict crop yield from facts about a field, then uses that model as a *practice field inside the computer* to ask two questions:

1. **How many extra tons does fertilizer add to a field?**
2. **As nitrogen, phosphorus and potassium go up, where does extra nutrient stop paying off?**

Everything is built from one script, [`crop_yield_pipeline.py`](crop_yield_pipeline.py), which also draws every chart and flowchart in this document.

> **Read this first: the data is synthetic.** The Kaggle dataset behind this project was generated by a program, not collected from farms (evidence in [section 4.2](#42-reality-check-does-the-data-behave-like-real-farms)). Every pattern the model finds reflects the rules used to generate the data. So this repository is a demonstration of **method** (cleaning, validation, modelling, honest interpretation), **not** a claim about real agriculture.

## TL;DR

| Question | Answer (on this synthetic data) |
|---|---|
| How well can we predict yield? | A random forest misses by about **2.09 tons** on fields it never saw (R² = **0.78**). Guessing the average misses by 4.42 tons, and a straight-line model by 3.31 tons. |
| How much does fertilizer add? | About **2.2 tons** per field, with the same size of benefit in every crop (2.11 to 2.26). No group of fields shows fertilizer being clearly wasted. |
| Where does extra nutrient stop paying? | Plateaus (95% rule): nitrogen **224**, phosphorus **85**, potassium **101** kg/ha. |
| How many fields sit beyond the plateau? | **6.9%** (N), **11.4%** (P), **11.8%** (K). This depends on the rule (range 3.2% to 11.2% for nitrogen). |
| What if we trim those fields back to the plateau? | Saves about **2.5% / 3.6% / 3.7%** of N / P / K, with a predicted yield change of **-0.03%**. |

## 1. Motivation and question

Farmers often apply more fertilizer than a crop can use, which wastes money and harms soil and water. This project was inspired by the **"AI for Low-Pesticide Agriculture"** idea on a list of Y Combinator startup requests, whose full version combines computer vision, robotics and biology. That is far more than one person can build, so I took the slice that data analytics can reach:

> **Where does adding more nutrient stop paying off in yield?**

An honest limit up front: **the dataset has no pesticide column** (see [section 3](#3-the-dataset)). The closest things are `fertilized` (yes/no) and the nutrient amounts, so this project studies fertilizer and nutrient levels, not pesticides.

### 4.1 Load and profile

Category balance is healthy: corn 59,932, wheat 58,986, rice 48,770, soybean 41,146, cotton 38,487 rows; 74% of fields are fertilized.

### 4.2 Reality check: does the data behave like real farms?

**Goal:** decide how far we can trust what the data will tell us. Real farms have structure: winters are colder, dry zones are drier, and inputs are linked. If none of that exists, the data was probably generated at random.

![Reality check](images/02_reality_check.png)

| Check | Real farms | This data |
|---|---|---|
| Temperature by season | winter much colder than summer | 24.2 to 24.3 C in every season |
| Rainfall by weather zone | "dry" far drier than "tropical" | 836 to 838 mm in every zone |
| Humidity by weather zone | varies by zone | 84.6% to 84.7% in every zone, including "dry" |
| Strongest link between two input columns | many strong links | **0.005** (essentially none) |

**Conclusion:** the inputs were generated independently at random, and yield was computed from them by a formula plus noise. So the patterns found later (hills, plateaus, the fertilizer effect) are most likely **the rules of the generator**, rediscovered by the model. That proves the *method* works, but it says nothing about real farms.

### 4.3 Cleaning

**Goal:** remove the empty cells in a defensible way. Most models cannot read an empty cell.

| Columns | Missing | Decision | Why |
|---|---|---|---|
| 8 columns (irrigation, nitrogen, rainfall, temperature, humidity, pest index, days from harvest, yield) | about 2 cells each | **drop those rows** (16 rows in total) | negligible loss |
| `soil_ph`, `phosphorus_kg_ha`, `potassium_kg_ha` | 8 to 12% | **fill with the median** | dropping all three together would lose about a quarter of the data |

**An assumption I tested before using it.** I expected soil-type-specific medians to be more accurate than one global median. The data said otherwise: the medians barely differ across soil types (soil pH 6.50 to 6.52, phosphorus 56.3 to 56.8, potassium 67.0 to 67.4). So the simpler **global median** was used.

| Column | Cells filled | Median used |
|---|---|---|
| `soil_ph` | 19,919 | 6.51 |
| `phosphorus_kg_ha` | 29,697 | 56.57 |
| `potassium_kg_ha` | 24,887 | 67.20 |

Result: **247,305 rows and 0 missing cells.** Side effect to remember: filling thousands of cells with one value creates an artificial **spike** in those columns' histograms (visible in [section 4.11](#411-sizing-the-over-application-sensitivity-and-trim-test)).

### 4.4 Exploration

**Goal:** see what yield looks like and which facts relate to it, before modelling.

**The target is a clean bell curve.** Mean 23.72 and median 23.72 tons, skewness 0.02, no negative or zero values. The few outliers at both ends are the natural tails of a bell curve, so they were kept.

![Target distribution](images/03_target_distribution.png)

**Fertilized fields yield more.** 24.30 vs 22.06 tons, a gap of **2.23 tons** (about 10%). This is the clearest raw signal.

![Fertilizer effect](images/04_fertilizer_effect.png)

**No single fact is strongly correlated with yield.** The largest are nitrogen (+0.15) and pest index (-0.15). Yield depends on many weak effects combined, which is a reason to use a model with many inputs instead of one rule.

![Correlations with yield](images/05_correlations.png)

**But correlation can hide a hill.** Correlation only measures straight-line relationships. Rainfall's correlation with yield is -0.05 and temperature's is +0.08, which look like "no relationship", yet yield clearly peaks in the middle of both ranges (best average yield 24.8 tons near 765 mm of rain and 24.9 tons near 26 C). A straight line cannot represent a hill. This is the main reason a straight-line model will fall short later.

![Hill shapes](images/06_hill_shapes.png)

**Does fertilizer help more in some conditions?** I checked this directly instead of assuming it. Inside every crop, soil type, rainfall band and temperature band the gain is between **2.13 and 2.29 tons** (overall 2.23). The benefit is steady, so there is **no group where fertilizer is clearly wasted**.

![Fertilizer gain by condition](images/07_fertilizer_gain_by_condition.png)

> This corrected an earlier guess of mine ("fertilizer helps more in poor soil"). Testing a story before telling it is part of the method.

### 4.5 Preparation: words to numbers and a fair exam

**Goal:** make the data readable by a model, and set aside a hidden exam so the model can be graded honestly.

**Encoding.** Models only do arithmetic on numbers. The method depends on the kind of column:

![Encoding decisions](images/flow_05_encoding.png)

*Why one-hot with `drop_first`?* Numbering crops 1, 2, 3 would invent a fake order (is rice "bigger" than corn?). One-hot makes one 0/1 column per category; dropping one avoids redundant columns, and the dropped category (**corn**) becomes the **baseline** that other crops are compared against. This matters when reading weights: "rice = -5.3" means 5.3 tons less **than corn**.

**Train/test split.** 80% of fields are used for learning and 20% are hidden until final scoring (`random_state=42`). If a model were graded on fields it had studied, a perfect score could just mean it memorised them.

| | Study set | Hidden exam set |
|---|---|---|
| Fields | 197,844 | 49,461 |
| Average yield | 23.724 | 23.706 |
| Share fertilized | 0.742 | 0.740 |

The two sets look alike, so the exam is fair. After encoding there are **28 features**.

### 4.6 The model ladder: from a guess to a straight line

**Goal:** build simple models first, so every improvement is measured against something. Each step fixes one weakness of the step before.

![Model ladder flowchart](images/flow_02_model_ladder.png)

**How models are scored (two numbers).**

- **RMSE** (typical mistake, in tons): square each error so + and - do not cancel, average them, take the square root. *Example with three fields:* actual 25, 20, 24 and predicted 24, 21, 24 give errors 1, -1, 0, squares 1, 1, 0, average 0.667, so RMSE = sqrt(0.667) = **0.816 tons**.
- **R²** (share of yield differences understood, 0 to 1): `1 - (model's squared error / squared error of always guessing the average)`. In the same example the lazy guess (23 tons everywhere) has squared errors 4 + 9 + 1 = 14, the model has 2, so R² = 1 - 2/14 = **0.857**.

**Level 0: always guess the average (4.42 tons, R² 0.00).** The floor. Any real model must beat it.

**Level 1: use one fact.** With only `fertilized`, the learned recipe is `yield = 22.07 + 2.22 x fertilized`, which just reproduces the two group averages. Typical mistake 4.30 tons, R² 0.05: one fact explains about 5% of the differences.

**Level 2: a straight line on all 28 facts.** The recipe becomes a long weighted addition: `yield = intercept + (weight x fact) + ...`. Typical mistake **3.31 tons**, R² **0.44**. The study and exam scores match (0.437 vs 0.439), so it is not memorising.

*One prediction worked by hand* (first hidden field): intercept 18.813 + sum of weight x value 4.061 = **22.874 tons** (actual 22.134). The largest contributions were: `crop_type_rice` -5.29, `seed_quality` +2.97, `nitrogen_kg_ha` +2.38, `fertilized` +2.19, `avg_temp_c` +1.74, `irrigation_method_flood` -1.20.

**Reading weights without being fooled:**
1. Crop weights are relative to the dropped baseline (corn).
2. Never compare weights across features with different units (nitrogen's per-kg weight is tiny but it spans hundreds of kg).
3. A near-zero weight can hide a hill (rainfall's straight-line weight is almost zero).

**The weakness:** the model draws only straight lines. In the chart, the dots form a tilted cloud instead of hugging the dashed line: it squeezes its guesses toward the middle and cannot see hills or crop-specific effects.

![Predicted vs actual](images/10_predicted_vs_actual.png)

### 4.7 Decision trees and overfitting

**Idea: a decision tree is a game of 20 Questions.** It asks yes/no questions about a field; each answer sends the field down a branch until it lands in a final box, whose number is the average yield of the training fields that landed there. It picks each question by trying thousands of options and keeping the one that splits the fields into the most similar groups.

Here is a real tree limited to 3 questions in a row (`max_depth=3`). `crop_type_rice <= 0.5` means "is the crop rice? No":

```text
|--- crop_type_rice <= 0.5
|   |--- crop_type_cotton <= 0.5
|   |   |--- rainfall_mm <= 1058.5
|   |   |   |--- value: [25.6]
|   |   |--- rainfall_mm >  1058.5
|   |   |   |--- value: [22.6]
|   |--- crop_type_cotton >  0.5
|   |   |--- rainfall_mm <= 928.5
|   |   |   |--- value: [22.6]
|   |   |--- rainfall_mm >  928.5
|   |   |   |--- value: [18.5]
|--- crop_type_rice >  0.5
|   |--- avg_temp_c <= 22.5
|   |   |--- rainfall_mm <= 1022.5
|   |   |   |--- value: [17.9]
|   |   |--- rainfall_mm >  1022.5
|   |   |   |--- value: [21.5]
|   |--- avg_temp_c >  22.5
|   |   |--- rainfall_mm <= 1055.5
|   |   |   |--- value: [21.6]
|   |   |--- rainfall_mm >  1055.5
|   |   |   |--- value: [25.6]
```

Notice that the rainfall cutoff differs by crop (cotton loses yield at lower rainfall than the corn, wheat and soybean branch, and rice prefers more rain). A straight line has just **one** weight for rainfall for all crops, so it cannot do this.

**What if the tree may ask more questions?** I tried depths from 1 to unlimited and scored each on the study fields (practice paper) and the hidden fields (real exam):

![Overfitting curve](images/09_overfitting_depth_sweep.png)

| Depth | Study R² | Hidden R² | Final boxes |
|---|---|---|---|
| 1 | 0.101 | 0.098 | 2 |
| 2 | 0.232 | 0.227 | 4 |
| 3 | 0.321 | 0.316 | 8 |
| 5 | 0.454 | 0.454 | 32 |
| 8 | 0.590 | 0.585 | 256 |
| 12 | 0.727 | 0.683 | 3,685 |
| 20 | 0.929 | 0.626 | 83,920 |
| no limit | 1.000 | 0.559 | 197,734 |

**This is overfitting.** The study score only rises, while the hidden score peaks (best: depth **12**, R² 0.683) and then falls. The unlimited tree scores 1.000 on the study fields but only 0.559 on hidden ones, building 197,734 boxes for 197,844 fields (almost one per field): it memorised the practice paper. **A training score that keeps climbing while the test score drops is the warning sign.** Even the best single tree already beats the straight line, but it is jumpy: change a few study fields and it picks different questions.

### 4.8 Random forest

**Idea: the wisdom of the crowd.** Guess the jelly beans in a jar: any one person is off, but the average of many guesses is usually close, because errors in different directions cancel. A random forest does this with trees:

1. Each tree trains on its own random re-draw of the study fields (draw names from a hat, putting each back).
2. At each question a tree looks at only a random handful of facts, so trees differ.
3. `min_samples_leaf=30` forces every final box to rest on at least 30 fields, which stops memorising.
4. The forest's answer is the **average of all trees' answers**.

![Random forest flowchart](images/flow_03_random_forest.png)

*Voting on one real hidden field:* the first eight trees guessed 25.56, 24.32, 22.77, 26.18, 22.82, 24.72, 27.58, 24.55 tons; the average of all 60 was **24.61 tons**, the straight-line model said 22.87, and the actual yield was 22.13. On this single field the straight line happened to be closer, which is fine: one field proves nothing. The exam is all 49,461 hidden fields.

**Do more trees help?** Yes, with diminishing returns:

| Trees voting | Hidden R² | Typical mistake (tons) |
|---|---|---|
| 1 | 0.702 | 2.412 |
| 3 | 0.752 | 2.201 |
| 10 | 0.769 | 2.121 |
| 30 | 0.774 | 2.098 |
| 60 | 0.776 | 2.091 |

![More trees](images/11_more_trees.png)

**Fair comparison of every model** (study vs hidden fields; the gap is the overfitting detector):

| Model | Study R² | Hidden R² | Gap | Hidden typical mistake (tons) |
|---|---|---|---|---|
| Average guess | 0.000 | 0.000 | 0.000 | 4.417 |
| One fact (fertilized) | 0.048 | 0.051 | -0.002 | 4.304 |
| Straight line (all facts) | 0.437 | 0.439 | -0.002 | 3.307 |
| One tree (depth 12) | 0.727 | 0.683 | 0.044 | 2.486 |
| One tree (no limit) | 1.000 | 0.559 | 0.441 | 2.934 |
| Random forest (60 trees) | 0.814 | 0.776 | 0.038 | 2.091 |

The forest has a high hidden score **and** a small gap: it learned real patterns. It becomes our practice field for the what-if tests.

![Model ladder results](images/08_model_ladder.png)

**What does the forest rely on?** Temperature and rainfall rank at the top even though their correlations with yield were near zero: the forest can see the hills. A caution: *importance* measures how much the forest used a fact, **not** how many tons it adds (fertilizer ranks lower yet adds about 2.2 tons).

![Feature importance](images/12_feature_importance.png)

### 4.9 Fertilizer what-if test

**Goal:** estimate how many extra tons fertilizer adds. In real life you cannot grow the same field twice, once with fertilizer and once without. In the computer you can: copy every hidden field, switch **only** `fertilized` (on in one copy, off in the other), and predict both. The difference is the estimated benefit.

```python
gain = forest.predict(X_test.assign(fertilized=1)) - forest.predict(X_test.assign(fertilized=0))
```

**Result:** an average gain of **2.20 tons**, matching the raw gap (2.23) from exploration. Two different methods agreeing is a good sign. By crop the model and the raw data agree to within 0.15 tons:

| Crop | What-if (model) | Raw gap (data) |
|---|---|---|
| corn | 2.19 | 2.34 |
| cotton | 2.20 | 2.22 |
| rice | 2.21 | 2.19 |
| soybean | 2.11 | 2.20 |
| wheat | 2.26 | 2.30 |

**A careful reading of the spread.** Single fields range from about 0.9 to 3.9 tons (middle 90%), and a few even show a *negative* gain (minimum -2.2). A negative benefit from fertilizer is not believable, and the raw data shows the same gap in every group, so this spread is most likely the **forest's own noise on single fields**. Trust the average and the group results, not single-field estimates.

![Fertilizer what-if](images/13_fertilizer_whatif.png)

### 4.10 Nutrient curves and the 95% plateau rule

**Goal:** find where extra nitrogen, phosphorus or potassium stops paying off. Same trick as the what-if: take 6,000 fields, set one nutrient to a low value for **all** of them, record the forest's average predicted yield, raise the nutrient step by step (40 amounts, skipping the thin extreme 2% at each end), and plot the averages. All three curves are **S-shaped**: flat, steep, then flat again.

**Eyeballing "where it flattens" is not defensible, so I used a rule:**

> **The plateau is the first amount at which the curve has already earned 95% of the total gain it will ever earn.**

*Phone-battery analogy:* charging to 95% is quick; the last 5% takes forever and barely changes anything.

![Plateau rule](images/flow_04_plateau_rule.png)

Worked on nitrogen: start 23.05 t, end 24.38 t, total gain 1.33 t; 95% line = 23.05 + 0.95 x 1.33 = 24.32 t; the curve first reaches it at **224 kg/ha**. Everything to the right is "the last 5%": 59 kg/ha more nitrogen buys only 0.06 extra tons.

```python
def plateau_at(curves, col, pct=0.95):
    grid, pred = curves[col]
    target = pred[0] + pct * (pred[-1] - pred[0])      # the 95% line
    return float(grid[int(np.argmax(pred >= target))])  # first amount at or above it
```

![Plateau rule on nitrogen](images/14_plateau_rule_nitrogen.png)

| Nutrient | Total yield gain across range | 95% line | Plateau |
|---|---|---|---|
| Nitrogen | 1.33 t | 24.32 t | **224 kg/ha** |
| Phosphorus | 0.38 t | 23.81 t | **85 kg/ha** |
| Potassium | 0.48 t | 23.86 t | **101 kg/ha** |

![All three nutrient curves](images/15_nutrient_plateaus.png)

Three honest warnings: (1) the three panels use **different y-scales**, so compare the totals in the table, not the slopes by eye; (2) the curves show what the model learned (an **association**), not proof that changing an input would cause that yield; (3) it is unclear whether the nutrient columns are amounts **applied** or **measured in the soil**.

### 4.11 Sizing the over-application, sensitivity and trim test

**How many fields sit beyond each plateau?**

| Nutrient | Plateau (kg/ha) | Fields above | Average excess (kg/ha) | Excess as % of all nutrient |
|---|---|---|---|---|
| Nitrogen | 224 | 6.9% | 47.9 | 2.5% |
| Phosphorus | 85 | 11.4% | 18.7 | 3.6% |
| Potassium | 101 | 11.8% | 21.7 | 3.6% |

Most fields are *below* each plateau, so over-application is a long thin tail, not the typical field. (The tall spikes in the phosphorus and potassium histograms are **not real**: they are the cells filled with the median in [section 4.3](#43-cleaning).)

![Fields beyond the plateau](images/16_fields_beyond_plateau.png)

**Does the answer depend on the 95% rule?** Yes, a lot. A looser rule (90%) puts the plateau earlier and flags more fields; a stricter one (99%) flags fewer. Never quote one number as "the truth": report the rule and the range.

| Nutrient | 90% rule | 95% rule | 99% rule |
|---|---|---|---|
| Nitrogen | 200 kg/ha (11.2% of fields above) | 224 kg/ha (6.9% of fields above) | 259 kg/ha (3.2% of fields above) |
| Phosphorus | 78 kg/ha (16.4% of fields above) | 85 kg/ha (11.4% of fields above) | 92 kg/ha (7.9% of fields above) |
| Potassium | 95 kg/ha (15.1% of fields above) | 101 kg/ha (11.8% of fields above) | 115 kg/ha (6.4% of fields above) |

![Sensitivity to the rule](images/17_sensitivity.png)

**Trim test.** I set every nutrient above its 95% plateau back down to the plateau (`np.minimum(value, plateau)`) and asked the forest to predict again:

| Measure | Value |
|---|---|
| Average predicted yield before | 23.719 tons |
| Average predicted yield after | 23.713 tons |
| Average change | **-0.006 tons (-0.03%)** |
| Fields losing more than 0.5 ton | 0.1% |
| Fields that did not change at all | 72.5% |
| Nutrient saved per field (N / P / K) | 3.3 / 2.2 / 2.6 kg/ha (2.5% / 3.6% / 3.7%) |

The saving is modest because 73% of fields were already at or below every plateau and did not change. Because the 95% rule leaves up to 5% of each curve's gain on the table, the yield change is not exactly zero.

## 6. Limitations and honest caveats

- **The data is synthetic.** Findings describe the generating rules, not real farms. This is the biggest limit.
- **No pesticide column.** The project studies fertilizer and nutrient levels, not pesticides.
- **Association, not cause.** The curves and what-if tests show what a model learned from patterns; they do not prove that changing an input would change yield.
- **Unclear nutrient meaning.** It is unknown whether `nitrogen_kg_ha` etc. are amounts applied or measured in the soil.
- **The 95% rule is a choice.** The sensitivity analysis shows how much the answer moves.
- **Single-field what-if estimates are noisy.** Trust averages and group results.
- **Small data-leakage:** median fill-in values were computed on all rows before the train/test split. The medians barely move, so the effect is negligible, but a stricter pipeline would compute them from the training rows only.
- **One split, one forest.** No cross-validation or hyperparameter tuning was done; the forest uses 60 trees and `min_samples_leaf=30` without a search.
- **Imputation artifacts.** Median filling creates histogram spikes in `phosphorus_kg_ha`, `potassium_kg_ha` and `soil_ph`.

## 7. Skills demonstrated

- **Data profiling and validation:** missing-value analysis, category balance, and a reality check that detected synthetic data.
- **Cleaning with evidence:** testing an imputation assumption before using it, and documenting side effects.
- **Exploratory analysis:** distributions, correlations, and spotting where correlation misleads (non-linear hills).
- **Feature preparation:** binary, ordinal and one-hot encoding; train/test splitting; leakage awareness.
- **Modelling and evaluation:** baselines, linear regression, decision trees, random forests; RMSE and R²; train-vs-test comparison to detect overfitting.
- **Interpretation:** reading coefficients and feature importance without over-claiming; what-if (counterfactual) analysis; response curves.
- **Analytical judgement:** a rule-based threshold, sensitivity analysis, and honest reporting of limitations; correcting an earlier assumption when the data disagreed.
- **Communication:** a reproducible single-script pipeline with auto-generated charts and flowcharts.

## 9. Glossary

| Term | Plain meaning |
|---|---|
| Feature | One fact about a field (rainfall, soil type, fertilized or not) |
| Target | What we predict (crop yield in tons) |
| Train / test set | Fields the model studies / fields hidden for a fair exam |
| Overfitting | Memorising the practice paper instead of learning the topic |
| RMSE | Typical size of a mistake, in tons (lower is better) |
| R² | Share of yield differences the model understands, 0 to 1 |
| Coefficient / weight | How much a straight-line model adds per unit of a feature |
| One-hot encoding | One 0/1 column per category |
| Decision tree | A chain of yes/no questions ending in a guess |
| Random forest | Many different trees voting; the average is the answer |
| What-if test | Change one fact about a field in the computer and see how the prediction moves |
| Response curve | Average predicted yield as one input is raised step by step |
| Plateau | The amount where a curve has earned 95% of its total gain |
| Sensitivity analysis | Checking how much the answer changes when a choice (like 95%) changes |
